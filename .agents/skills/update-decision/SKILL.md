# 更新 CopyUp 决策

维护 `DECISION.md`，把它当作 CopyUp 的长期产品与工程记忆，而不是 changelog、排查记录或实现流水账。

## 工作流程

1. 先读 `DECISION.md`，理解现有分区、当前规则和潜在冲突。
2. 再读本次变更相关的事实来源，例如 git diff、代码、Xcode 配置、Info.plist、签名配置、TODO、DEVLOG 或测试。
3. 从实现、用户意图和产品方向里提炼候选决策。
4. 只保留长期有效、能指导未来产品和工程实现的决策。
5. 优先合并到已有 section；只有出现稳定的新主题时才新增 section。
6. 删除或改写过期、重复、过细、被当前代码推翻的条目。
7. 结束前通读 `DECISION.md`，确认没有明显冲突。

不要只根据聊天摘要更新 `DECISION.md`；只要仓库可读，就必须核对实际代码或 diff。

## 什么值得写

- 会影响后续产品方向、菜单交互、数据模型、命名口径、发行渠道、签名公证、第三方服务或商业化边界。
- 能避免以后重复争论或重复犯错。
- 是稳定规则，而不是某次改动的文件清单。

不要写一次性 bug 排查、临时 workaround、测试命令、发布说明、实现过程，或“怎么发现问题”的叙述。

## 清理规则

- 删除已经被当前实现替代的旧决策。
- 合并重复表达。
- 把仍然正确但太贴近实现细节的内容改成行为级规则。
- 不保留兼容、fallback、桥接、临时过滤类过期方案，除非当前系统仍明确依赖它。
- 不因为本次没改某块代码就删除仍然有效的架构约束。

## 写法规则

- 使用现在时和规范性语气。
- 每条尽量一句话。
- 避免“最近”“这次”“我们决定”“因为 bug”这类过程语言。
- 优先写产品行为、工程边界和命名口径，少写文件名。
- 只有文件、表、字段或 API path 本身就是契约时才写出来。
- 保持文档精简；不能指导未来实现的条目应该删除。

## 验证

- 检查 `DECISION.md` 没有明显冲突、旧方案残留或过程化条目。
- 必要时搜索和本次决策相关的旧关键词，确认旧方案没有残留。
- 跑 `git diff --check`。
- 保持 Markdown 简洁可读；本仓库不要求使用前端格式化工具处理 `DECISION.md`。
